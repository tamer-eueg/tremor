# API Contract-Drift Auto-Patcher — Proof of Concept

**What this tests:** whether the core technical claim holds — that a program can automatically detect breaking changes in a third-party API and generate the code patch to fix an integration, without a human reading changelogs.

**Test data:** two real, historical versions of a real public API's official OpenAPI spec — GitHub's own REST API, fetched from GitHub's own `github/rest-api-description` repository:
- OLD: tag `v1.0.0` (428 documented endpoints)
- NEW: tag `v2.1.0` (561 documented endpoints)

No synthetic or invented data. This is what GitHub's API actually looked like at two real points in its history.

## Result

The diff engine (`diff_engine.py`) found **213 total changes** between the two versions:

| Severity | Count |
|---|---|
| Breaking (would silently break an existing integration) | **41** |
| Non-breaking (new endpoints, new optional fields) | 172 |

Breakdown of the 41 breaking changes:

| Kind | Count |
|---|---|
| Endpoint removed entirely | 26 |
| Request body field became required | 9 |
| Parameter removed | 4 |
| HTTP method removed from an endpoint | 1 |
| Query parameter became required | 1 |

The full list is in `diff_report.json` — every one of these 41 is a real change a real company's GitHub integration would have had to deal with, somewhere between early 2020 and today.

## Worked example: from detection to patch

One finding: `POST /repos/{owner}/{repo}/pulls/{pull_number}/comments` (add a review comment to a pull request) used to accept `commit_id` and `line` as optional fields. In the newer spec, both are required.

Any code written against the old spec would have worked for months, then started getting rejected by GitHub with a 422 error the moment this shipped — with nothing in the code itself explaining why.

`example_patch.py` shows the before/after:
- **Before:** the original integration function, exactly as it would have been written against the old spec.
- **After:** the same function, auto-patched — the two newly-required fields are added to both the function signature and the outgoing request body, with a comment citing the exact spec change that caused the edit.

Run it yourself: `python3 example_patch.py`

## What this proves

- Real breaking changes in a real, actively-maintained API are common enough (41 in one version span) that a monitoring layer has something genuine to catch.
- The diffing logic that finds them is a well-scoped, deterministic software problem — no API keys, no partnerships, no industry-specific knowledge required.
- Turning a detected change into a code patch is mechanical once the change is classified — the example above was generated by reading the diff output and rewriting the function accordingly.

## What this doesn't cover yet (honest scope)

- **Response-body schema changes** (a field disappearing from what the API *returns*, rather than what it *accepts*) aren't diffed yet — this prototype focuses on request-side changes, which are the ones that cause hard failures rather than silently-wrong data.
- **The patch generation above was done by reasoning over the diff output**, not by a fully automated code-rewriting pipeline yet — the production version would point an LLM at the affected source file plus the diff entry and have it produce the patch as a pull request.
- **This only watches one API right now.** A real product needs a scheduler that periodically re-fetches specs (or subscribes to changelogs) for every API a customer depends on, and a place to store/display findings over time.
