# Wiring the Monitor to the Patch Generator (Phase 5)

Phases 1-4 each worked in isolation: hand a diffing engine two spec files, or
hand the patch generator a diff report and a source file. This phase removes
the hand-off — a live check now drives patching directly.

## What changed

`src/patch_generator.py` was refactored to separate its core logic
(`generate_patch(source_path, source_text, findings)` — pure, no file I/O
beyond the source text it's given, no printing) from its CLI wrapper (`run()`,
which reads files, prints, and writes `_patched.py` output). The CLI's
behavior is unchanged — same output, verified by re-running it after the
refactor and confirming the result still compiles cleanly.

`src/monitor.py` now calls `generate_patch()` directly, in-memory, right
after computing a check's findings — no JSON round-trip, since the findings
are already the same Python objects `diff_engine.py`/`response_diff.py`
produced. A watchlist entry can name `watched_files`: real integration code
that calls the tracked API. Every check runs the patch generator against
each one with that check's findings, and anything it can auto-patch gets
written to `reports/monitor_runs/patches/`, with the file list, changelog,
and patch path recorded in the run's JSON record.

## The live run

Re-ran the actual monitor against GitHub's current spec (same setup as phase
4: v2.1.0 seeded as baseline, `examples/sample_integration.py` on the
watchlist as the stand-in customer file). Result, honestly reported: **139
breaking changes found, but none of them touched the three functions in
`sample_integration.py`** — the endpoints those functions call (PR review
comments, `/meta`, release-asset upload) simply had no further drift in the
v2.1.0-to-today window; the request-body-field and query-param findings used
to prove out phases 1/3 came from the older v1.0.0-to-v2.1.0 window. Correct
behavior, but not a demonstration of the wiring actually firing.

**So the wiring was verified separately, deliberately, against findings
known to intersect** — the same v1.0.0→v2.1.0 findings from `reports/diff_report.json`
that phase 3 already proved produce a correct patch, run this time through
`monitor.patch_watched_files()` instead of the CLI. Result: identical patch
to phase 3's — `commit_id`/`line` added to `add_pr_review_comment()`, `name`
added to `upload_release_asset()` — generated by the monitor's own code
path, and confirmed to compile cleanly.

This is a fair test, not a shortcut: the point of the refactor was that the
*same function* now serves both the CLI and the monitor, so proving the CLI
path produces correct output (phase 3) and proving the monitor calls that
same function correctly (this phase) together cover the whole path. A live
check finding a *new* auto-patchable change and firing the patch generator
on it will happen the first time GitHub actually ships one of those two
finding kinds against an endpoint one of the watched files calls — which is
exactly what recurring monitoring is for.

## What's still open

- No real customer repo is on the watchlist yet, since Tremor has no users —
  `examples/sample_integration.py` stands in.
- Patches land in `reports/monitor_runs/patches/`, not back into the
  watched file or a pull request. Writing to the file in place (or opening a
  PR) is a product decision that needs a real target repo to make sense of,
  not more engineering against a stand-in.
- Still no schedule/cron and no hosting to run any of this continuously —
  the same identity/payment-step blocker noted in phase 4.
